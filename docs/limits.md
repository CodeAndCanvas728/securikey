# What SecuriKey does not do

The short list is in the [README](../README.md#limits-at-a-glance). This is the full one. `tests/test_known_bypasses.py` pins several of these as tests, so they cannot drift quietly.

## A failed call is not redacted, unless `skey run` started it

Claude Code runs `PostToolUse` only when a tool succeeds. A Bash command that exits non-zero (`curl -f` on a 401, a script that crashes, `cat file; false`) fires `PostToolUseFailure` instead, and a hook cannot rewrite that error text. Checked on Claude Code 2.1.316:

- A command that printed a token and exited 3 gave the model the raw token.
- The `PostToolUseFailure` hook can detect a secret in the error and warn (`skey hook failure`), but it cannot stop the turn: a `continue: false` was logged and the next turn still ran in `claude -p`, so the hook sends a message to the user and a note to the model instead.
- Rewriting the command so it always succeeds is refused by Claude Code's own permission check (tried: an `EXIT` trap, an appended `echo`, a `{ ... } ||` group), so the plugin does not try.

What covers it: **`skey run` filters its own command's output** when stdout is piped (which is how an agent runs it). A failing `skey run --env T=name -- cmd` prints `[securikey:name]`, not the value, and still exits with the command's status. Verified end to end in Claude Code with a throwaway keychain service. Costs: a piped child can buffer or colour differently, and output is held back by up to 4096 characters or 0.25 seconds so a value split across two reads is still found (a stored value that spans lines is held back for the full window even across a pause). Binary output passes through byte for byte. If the watch list (rotated-out values, values fetched from Paperclip) cannot be read, the filter warns on stderr and still redacts the stored secrets, or fails closed under `SECURIKEY_HEADLESS=1`.

`SECURIKEY_RUN_FILTER=0` turns the filter off, for a program that cannot run behind one. It is a convenience, not a control: anything that can set an environment variable on a command can also pipe a value through `rev` (see below), so it does not widen what a hostile agent can already do. At a terminal `skey run` replaces itself with the command and filters nothing.

What is still exposed: a command that fails and printed a secret it did not get through `skey run` (a file it read, a variable already in the environment). Rotate a secret that was printed. The warning is pinned in `tests/test_hooks.py::FailedToolCallTest`, the filter in `tests/test_runfilter.py`.

## Output

- A command can't be un-run: a script that sends a secret over the network still sends it. Redaction controls what the **model** sees.
- Claude Code's local transcript and telemetry record tool output before a hook replaces it, and a blocked prompt can still appear in local prompt history. The guarantee is about the model and the API, not your disk.
- A command can transform a secret before it prints it, and the transformed text is not redacted. Redaction matches the stored value and its base64 and URL-encoded forms, nothing else: `skey run --env A=key -- sh -c 'echo $A | rev'` prints the value reversed, and hex, a value split across lines or output, or one with a separator between every character pass through the same way. `skey run` hands the value to the command you chose; it cannot judge what that command does with it.
- A secret in an unknown format that you never stored can't be recognised. Store it (`skey add`) and it is covered exactly. That includes a JWT written directly after a token character (`token-eyJ...`): the pattern does not start a match inside a run of token characters, which is what keeps it linear-time (a run of `-eyJ` used to stall the hooks). A stored JWT is matched exactly wherever it appears. Pinned in `tests/test_known_bypasses.py`.
- A stored value shorter than eight characters is not matched exactly, so it is not redacted. Short secrets are not really secrets, but the plugin will not pretend otherwise.
- If the keychain is locked, the hooks fall back to pattern matching only. A stored secret in a format the patterns do not know would then pass through unredacted; you are told when this happens.
- A private key is redacted whole, so everything after a `-----BEGIN ... PRIVATE KEY-----` line goes with it (RSA, EC, OPENSSH, ENCRYPTED, SSH2 ENCRYPTED and PGP `... PRIVATE KEY BLOCK` headers). A documentation page that quotes a key header will have the rest of the page redacted too.
- A file on a stalled network mount (NFS, CIFS) can still block the hook until its timeout. The hooks fail closed, so such a call is denied or the output replaced, and the session stops until it times out.

## Dotenv files

- The name guard allows a short list of commands that cannot print a file's contents: `skey import`, `skey add`, `skey rm`, `skey list`, `skey warm`, `skey patterns`, `git status`, `git ls-files`, `git check-ignore`, `git rev-parse`, `ls` and `test`. Everything else that names a dotenv file is blocked, `find . -name '*.env'` and `rsync --exclude '*.env'` included: they are safe to run, but `find` can print a file with `-exec`, so they are not on the list. A command that reaches a dotenv file through a shell expansion (`ls $(cat .env)`) is blocked too, because the command that runs is not the one that is written.
- **A mention is allowed only in one simple command.** The gate reads the command as shell (`plugin/securikey/shellparse.py`: quotes, redirects, heredocs, `$(...)`), not as raw text. A name is not a read when the whole call is **one** command (no `&&`, `;`, `|`, `||`) that holds no substitution, runs a program the gate can name, has no input redirect and writes at most one file, and that command is `echo`/`printf`, `git commit` with plain options (`-m`, or `-F -` with a heredoc), a `grep`/`rg` whose pattern is the name, or a single heredoc to `cat`, `tee`, `tea` or `gh`. A `;`, `&&`, `|` or the word "read" inside a quoted string is just text. Everything else that names a file is read as before: it is a read when the name is an input redirect (`< NAME`, `<<< NAME`), an argument to a program that is not on the list above, inside `$(...)`, backticks or `<(...)`, or in a heredoc fed to something that can open files.
- **A call of several commands that names a dotenv file is denied**, as it was before this rule, even if every command is harmless (`mkdir -p d && cat > d/note.md <<'EOF' ... NAME ... EOF`). So is a name inside a `bash -c` script, a heredoc to a shell, a substitution or a process substitution, and a program given by path or expansion. The message says so; split the call, or write the note with the Write tool. Why: whatever else is in a chained call (a second command, a nested shell, `>(bash)`) can make text in one command open the file through another, and six review rounds each found one more way. The rule does not try to prove a chained call safe.
- **Denied by design, though nothing is read:** a heredoc fed to an interpreter (`python3 - <<'EOF'`, `node`, `ruby`) whose body names a dotenv file, because the body is code that can open it. Text that names a file and goes into a pipe (`echo NAME | cat`). More than one heredoc on a command. Any `$(...)` or backtick that names the file, even inside `echo`. Shell the reader does not model fails closed when it holds a name: `${...}`, `$'...'`, subshells and groups, `if`/`for`/`while`/`case`, an unclosed quote, a heredoc with no closing line, more than 500 commands, and a command over 64 KB. The denial message says which word matched. Such a command with no literal name in it is not denied, as before: a name built by an expansion (`cat $'\x2e...'`) is not seen, and the output redaction below covers it.
- **What counts as a finding on this guard:** (a) one simple command on the list above that leads to a read, or (b) a call of several commands, a substitution or a nested shell that names a file and is allowed. Any other spelling (a name built by an expansion, a nested `skey run` the hook cannot read, text written in one call and run in another) is a known layer gap, covered by the output redaction and the run filter, and listed here.
- **Accepted gap:** text written to a file in one call (`echo 'cat NAME' >> run.sh`, a heredoc to a file, the Write tool) can be run in a later call. A text-only check cannot see that; the output redaction below is what covers it.
- Names matched: `.env`, `.envrc`, `.env.<suffix>`, `.env-<suffix>`, `.env_<suffix>`, and `prod.env`, `production.env`, `dev.env`, `staging.env`, `test.env`, `local.env`, `live.env`, `secrets.env`, `credentials.env`, in any case and with simple quoting. `process.env` and `.environment` are not names. The content scan below reads any file named `*.env`.
- `skey run` is checked as the command it runs, and it may only inject a file whose values are all names. A file that still holds a plaintext value is refused, because `skey run` would put it into the child's environment.
- The name check is not the guarantee. The hook also reads the project's own dotenv files and redacts their secret-looking values from every output, so a read it can't see by name (a glob, `$(...)`, a script) still doesn't reach the model, as long as the file still has its name when the output is checked. A command that moves the file first (`cat .en?; mv .en? notes.txt`) gets past the scan. That is an accepted gap. A glob that spells no env-file name (`cat *.local`, `head *.backup`) is not denied at all, because denying every `*.local` would block ordinary files; the output redaction covers it, but only when the command succeeds (see the failed-call section above). A test pins this.
- A single line of output over 1 MB that is still unfinished when the limit is reached is withheld from `skey run`'s output and replaced by a notice, rather than released in part, because a part could cut a token and print its start.
- What the scan covers: the files under the session's directory, depth 4 (deeper folders are skipped without a warning), build folders skipped, a walk limit, 4 MB read per call, 1000 lines parsed per file (a secret after line 1,000 is not redacted; the file is reported by name), 500 values registered per call and shared out between the files (the usual names first), so one file full of values can't crowd out another. What is cut is reported by file name. A directory the command changes into is not scanned. A link that points out of the session's directory is not read, and the file that is opened is verified to be the file that was judged. Example files (`.env.example`, `.sample`, `.template`, `.dist`) are not scanned: they are meant to be committed, so keep real values out of them.
- Which values count: a value counts when it is a known token format, a credential-URL password, or sits under a secret-sounding key with a digit or mixed case. Whitespace at either end of a value is ignored (`KEY=" abc123 "` is judged as `abc123`); whitespace inside means a phrase, not a token, and it is left alone. Plain words (`NODE_ENV=production`), slugs, numbers, host:port, URLs without credentials, and paths that start with `/`, `./`, `../` or `~/` and have two or more segments never count. A lowercase-only passphrase under a secret key isn't treated as a secret either. This is a stricter rule than `skey import`'s.
- A credential URL's password is judged like any other value: it can't hold a `/` (`postgres://app:secret@db` counts, `postgres://replica:6333/db@host` doesn't), and a word is not a secret (`postgres://app:password@db` doesn't count, or every call that mentions a password field would be denied), nor are the placeholders every tutorial uses (`passw0rd`, `admin123`, `ChangeMe`).
- A base64 secret that happens to look like a path (`/abc.../xyz...`, about 1 in 170) is not redacted. A cloned repo can make the scan register words of its choosing (`A_SECRET=JavaScript`), so calls that carry them are denied: a nuisance, not a leak, and the label names `dotenv:KEY`.
- A dotenv file that holds `securikey:<name>` references only resolves when the command is started through `skey run --dotenv`. An application that reads the file itself sees the marker, not the value.
- `skey run --dotenv FILE` is allowed by the hook only when every value in FILE is empty or a reference. This is a best-effort layer, not a guarantee. Under it sits the check the hook has always made, on the command text (cut at `&&`, `||`, `;`, `|` and newlines, data-sink heredocs removed), and the layer only adds to it. On top of that the hook checks every `skey run` in a command, read as shell: behind a wrapper (`env`, `sudo`, `timeout`), nested (`skey run -- skey run ...`, followed 3 deep; a deeper one that holds `--dotenv` is denied), in a heredoc fed to anything that is not a plain data sink (`cat`, `tee`, `git`, `tea`, `gh`) or printer, shells and wrappers included (`env bash <<EOF`), and in a `$(...)` or backtick body, whether or not the text names a dotenv file. A `-c` script is followed only for a bare shell (`bash -c ...`): behind a wrapper (`env bash -c ...`) or after another option (`bash -o pipefail -c ...`) it is scanned for dotenv names only. The work is bounded: one call may parse 256 KB in all, nested payloads included, or it is denied, at most 8 `skey run` words are judged, and each dotenv file is read once per call and at most 4 MiB of them in all (a file past that is treated as not imported). Known gaps, which will not be closed one spelling at a time: a program it cannot read (`S=skey; $S run ...`), a flag built by an expansion (`skey run $'--\x64otenv' ...`), a program spelled in another case (`SKEY run ...`, which runs on a case-insensitive file system), text a printer sends into a shell (`echo '...' | sh`, `cat <<'EOF' | bash`), a script written in one call and run in another, a sourced script that changes directory, and a wrapper option that changes directory (`env -C /srv skey run --dotenv F`, `sudo -D`: `F` is read from the session folder). The main text check has the same gaps. A review finding is worth fixing only if it is a regression against the previous release, a false positive on an ordinary command, or a crash or timeout; a new spelling goes on this list. What does not depend on the spelling is the run's own output filter: `skey run` redacts the secret-looking plain values it loads from a `--dotenv` file, wherever the file is, and says so on stderr. `SECURIKEY_RUN_FILTER=0` and a run at a terminal turn that filter off.

## Other harnesses: Vibe, Pi, OpenCode

`skey setup vibe|pi|opencode` installs shims that send each harness's payload to `skey hook <kind> --host <name>`, which maps it to the Claude event and runs the same checks. Checked against Vibe 3.1.2, Pi 1.5.2 and OpenCode 2.2.7 with a stub model server and a fake secret: a tool call holding the secret is denied, a command that prints it shows the model `[securikey:env:NAME]`, a failing command is redacted too (better than Claude Code, which cannot rewrite a failed call: Vibe's `post_tool`, Pi's `tool_result` and OpenCode's `execute.after` can), a prompt holding it is blocked, a broken `skey` path blocks the session, and `SECURIKEY_HOST_BYPASS=1` passes everything.

| | Vibe | Pi | OpenCode |
|---|---|---|---|
| Call input with a secret | denied (`pre_tool`), also for tools called inside `run_typescript` | denied (`tool_call`) | denied (`execute.before`, a throw blocks) |
| Output | replaced by the redacted text (`post_tool`) | `content`, `details` and `structuredContent` redacted (`tool_result`) | `content` and `output` redacted (`execute.after`) |
| Prompt | blocked (`pre_agent`) | blocked (`input`) | blocked (`session` prompt hook, a throw blocks) |

- **Not covered:** anything a harness wrote down before a hook ran, and what it keeps. Vibe's session journal under `~/.vibe/logs/session/` holds the original tool output, the tool call's input and a blocked prompt (seen on 3.1.2): the redaction protects what the model sees, not that file. OpenCode's stored history was not checked.
- **Vibe's `run_typescript`:** Vibe runs the hooks for the tools a script calls (`tools.file_system.bash` and the like), not for the `run_typescript` call itself. A script that returns a value it holds in its own code is not checked.
- **The agent can edit the hook files.** They sit in the harness's home (`~/.vibe/plugins/securikey`, Pi's `extensions`, OpenCode's `plugins`), and nothing here stops an agent that is allowed to write there from changing them. Protect them with the harness's own guards or file modes.
- **Names the guards know:** the shell and dotenv guards are keyed on each harness's built-in tool names (`bash`, `read`, `edit`, `grep`, `shell`, `read_file`, `process_start`, `process_write`, ...). A tool with another name (an MCP tool) still has every string in its input scanned for secrets, but is not read as a shell command or a file path. A call whose command or path cannot be read is denied, and so is one whose `command` and `cmd` (or `path`, `filePath` and `file_path`) hold different values: the guards judge one and the harness may act on the other.
- **Vibe's `process_write`** is judged one write at a time, as a command line. Input split across writes to a shell that is already running (`cat ` then the file name) is not put back together: each hook is a fresh process with no memory of the earlier writes. A secret in any one write is still denied.
- **What is scanned in a prompt:** its text. Attached files and images are not.
- **If OpenCode makes an error message read-only,** the plugin cannot rewrite it and the original text reaches the model without a notice (an `execute.after` hook cannot block). It was writable on 2.2.7.
- **An OpenCode tool error** (`status: "error"`, such as invalid arguments) has its message rewritten through `event.error.message`; the model saw the rewritten text. This was checked with a stand-in message, not with a secret in a real error.
- **Cost:** each hook starts `uv` once, as in Claude Code (p95 under 120 ms, measured by `python bench/hook_cost.py`). A hook that takes over 15 seconds is a failed check: the first keychain read after a reboot can ask for permission, so run `skey list` once from your terminal.
- `skey setup` runs only from your own terminal, because removing the hooks switches the protection off.

## Requests from an agent

`skey request` lets an agent queue a rotation, a sync or a configuration mark instead of waiting for you. It is a convenience, not a new control:

- The queue file is yours to read and the agent's to write (same user). Every entry is validated each time it is read, the text you are asked about is built from its fields and not from the agent's words (the agent's reason is shown, labelled as its own), and approving applies the copy you were shown, not a second read of the file. A forged "approved" entry runs nothing: only `skey approve` runs anything, and it refuses without a terminal. A writer can still mark a waiting request answered, which removes it from the queue without anyone saying yes; the agent could already delete the file. A name in the file that is not a stored secret (it may be a pasted value) is never printed, and a request whose reason holds a stored value or a token pattern is refused.
- The guarantee is the one the terminal check already gives. A process that opens its own pseudo-terminal can run `skey approve` and answer yes, exactly as it could run the commands directly, and `skey run --env` already hands a value to any command an agent picks.
- A request for a rotation with `--generate` makes the new value inside the process: nobody sees it, the agent included. The old value stays redacted for the usual seven days.

## Other

- The hooks in the plugin are Claude Code's. Vibe, Pi and OpenCode get the same checks from `skey setup` (previous section). The `skey` CLI works from any agent or shell.
- macOS and Linux are supported. On Linux the keychain needs a Secret Service provider (GNOME Keyring or KWallet). Windows is untested.
- `skey sync` and `skey rotate` are for your own terminal. The pre-hook denies a Bash call that names them (also nested, quoted or behind an expansion), but a text match on shell is never complete, and a process that opens its own pseudo-terminal gets past the terminal check: these are layers, not a sandbox. A command longer than 16 KB that names `skey`, `sync` or `rotate` is denied without being parsed.
